# 0003 — Cache-aside over write-through, and fail-open

**Status:** Accepted
**Date:** 2026-10-17
**Task:** TB-018

## Context

`GET /events/:id` is the hottest read in the system and, after TB-013's index, costs two Postgres queries and ~23 ms. The delivery plan wants Redis in front of it, as a decorator on `EventRepository` that nothing above L3 can see. Two questions had to be settled before writing it: which caching pattern, and what a read does while Redis is gone — because TB-017 left ioredis's offline queue on, so a `GET` issued during a reconnect waits rather than fails.

## Decision

**Cache-aside** (read-through on a miss, `SET … EX 300`, explicit `DEL` on a write), implemented as `CachedEventRepository` wrapping `PgEventRepository`, wired in the composition root only. **Fail-open, bounded:** when the client is not `ready` the cache is skipped; every cache command runs under a 100 ms deadline; a command that throws or exceeds it is a miss, logged. **Invalidation is fail-closed, bounded:** not `ready`, or past the deadline, throws — a swallowed `DEL` would serve the old row for 300 s, and a hung one is not fail-closed, it is a hang. Cached bytes are untrusted and are parsed through a Zod schema; a rejected payload is a miss, never an error.

## Alternatives considered

| Option                                                   | Why not                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Write-through (update Redis on every write)              | There is no event write path — the seed inserts once and nothing updates. Write-through has nothing to hang off, and it couples the writer to the cache's shape. When a writer appears, the decorator's own `save` wraps the inner `save` and issues the `DEL` after the Postgres commit — a `DEL` before it lets a concurrent miss re-cache the old row; L2 never learns there is a cache. TB-019a shows what forgetting it costs.                                                                                                                 |
| No cache at all                                          | The honest option on this data set: 23 ms is fine. Rejected because the project exists to learn the pattern and its failure modes (stale window, stampede, immortal keys), and TB-019 measures whether it buys anything against the _indexed_ baseline. If that row says no, this ADR says so here: it was built to learn, not because Postgres was slow.                                                                                                                                                                                           |
| Fail-closed (a Redis outage fails the read)              | Turns a cache outage into an outage. Worse: with the offline queue on it is not even a failure but a hang, up to 20 reconnect attempts. A cache that makes reads less available than no cache is wrong by definition.                                                                                                                                                                                                                                                                                                                               |
| The `status` guard alone, or a per-command timeout alone | Both are needed. The guard is known before issuing the command and costs nothing, so a read while Redis is known-down pays no timeout. But a command already on the wire when the socket dies is not rejected — ioredis re-sends it after the reconnect and rejects it only after `maxRetriesPerRequest` attempts (~74 s); the guard cannot see that, and only a deadline settles it. (`/health`'s `pingWithin` is the same idea in `presentation/`; two copies of a ten-line helper in two layers is a known smell, not fixed by cross-importing.) |
| Trust the cached JSON (no schema)                        | A different version of this code, a hand edit in RedisInsight, or a spike can write that key. The domain constructors would throw on a bad payload and the read would be a 500 for a cache problem. The schema is strict enough that what it accepts cannot fail them.                                                                                                                                                                                                                                                                              |
| Cache `listUpcoming` too                                 | A query over time under one key serves events that have already started until the TTL runs out. Pass-through.                                                                                                                                                                                                                                                                                                                                                                                                                                       |

## Consequences

**Good:** the boundary held — no controller, use case or DTO changed. Reads survive a Redis outage unchanged. A read whose cache command was on the wire when Redis died costs at most the deadline. A corrupt entry heals itself on the next read — unless its event no longer exists in Postgres, in which case nothing is rewritten and it warns on every read until its TTL expires.

**Bad / accepted trade-off:** up to 300 s of staleness after any change to an event (nothing changes events today). The first read of a cold key still pays Postgres, and under concurrency every concurrent miss does — the stampede TB-019 closes. Hit/miss are invisible until TB-019's counters.

**What would make us revisit this:** the cache key is built from the caller's spelling of the id (`z.uuid()` admits uppercase; Postgres matches either case), so two spellings are two entries and one `invalidate` clears one — harmless until a writer exists, then a normalisation at the `presentation/` boundary, outside this task; an event write path (then `invalidate` gets a caller, or write-through becomes worth its coupling); TB-019's benchmark showing the cache buys nothing measurable; a reason to cache the list (a `now`-bucketed key would be the shape).
